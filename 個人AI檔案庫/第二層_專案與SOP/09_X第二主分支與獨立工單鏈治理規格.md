# X 第二主分支與獨立工單鏈治理規格

- 文件狀態：CURRENT
- 適用專案：WHD
- 規格日期：2026-09-15
- Requirement Authority：使用者核准之「X 為第二主分支；A/B/C/D 各自建立獨立工單鏈；整鏈完成前不得受其他分支或 X 後續變動影響；整鏈完成後才可進入合回 X 的程序」
- 對應 Master：GitHub #262 `X independent task-chain governance — Master`
- Required Master chain：`T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7`
- 目前 X：`cleanup/2d-3d-sync`

## 1. 目的

本規格定義 WHD 在 `X` 作為第二主分支時，多個 Master 任務／工單組如何並行而不互相污染。

核心原則只有一條：**每個 Master 工單組是一條從 X 的固定快照出生、在完成前自行演進的封閉鏈。**

A、B、C、D 等不同工單組不得互相借 branch、commit、HEAD 或尚未整合進 X 的結果；active chain 也不得因 X 後續前進而 merge/rebase 最新 X 進來。

## 2. 名詞

### 2.1 X

WHD 的第二主分支／主要整合目標。現行值：

```text
X = cleanup/2d-3d-sync
```

本規格中的 X 是「integration target」，不是 active task chain 的持續 source。

### 2.2 Master Chain

一個完整任務／工單組，例如：

```text
A: A0 → A1 → A2 → ... → An
B: B0 → B1 → B2 → ... → Bn
C: C0 → C1 → C2 → ... → Cn
D: D0 → D1 → D2 → ... → Dn
```

每一條 Master Chain 有自己的 frozen base、work-order branch、accepted HEAD、child issue lineage、QA evidence 與 final chain HEAD。

### 2.3 FROZEN_X_BASE_SHA

某條 Master Chain 建立瞬間反讀到的 X HEAD。

一旦記錄，直到該 Master Chain 完成前不得改寫。

若 A/B/C/D 是同一批次同時建立，除非使用者另有指定，四條鏈應共用同一個 X snapshot SHA；若在不同時間建立，則各自在建立當下凍結自己的 X HEAD。

### 2.4 WORK_ORDER_BRANCH

該 Master Chain 的長期 lineage owner。所有 child task 的 accepted result 只能沿著此鏈往前累積。

### 2.5 CURRENT_X_HEAD

X 在某一時刻實際最新 HEAD。active chain 可讀取它做 drift / integration-readiness 比較，但不得直接把它灌進 active chain。

## 3. 不可變量（Invariants）

### I-01：一條 Master 一個 frozen base

建立 Master Chain 時必須先：

1. fetch / 反讀 X；
2. 記錄 `FROZEN_X_BASE_SHA`；
3. 從該 SHA 建立該 Master 的 `WORK_ORDER_BRANCH`；
4. 反讀 branch base，證明 branch 確實從 frozen base 出生。

沒有 base identity 就不得施工。

### I-02：active chain 不追 X

Master Chain 建立後，即使 X 有新 commit，active chain 也禁止：

- merge X → chain；
- rebase chain onto X；
- reset chain 到新 X；
- 用新 X HEAD 取代下一張 child ticket 的 parent；
- 因「X 比較新」而重開 child branch。

X 的變動只進入 drift audit / Integration Acceptance，不得改變 active chain lineage。

### I-03：兄弟鏈完全隔離

A、B、C、D 彼此禁止：

- merge；
- rebase；
- cherry-pick 尚未進 X 的 production change；
- 共用 temporary QA branch 當 production lineage；
- 把另一條 chain 的 accepted HEAD 當自己的 child base；
- 以另一條 chain 的 remote QA run 當自己的 acceptance evidence。

若 A 真正依賴 B 的尚未整合功能，A 必須停在 dependency gate，不能偷搬 B 的 commit。

### I-04：child 只接上一個 accepted HEAD

同一 Master Chain 中：

```text
T0 accepted HEAD → T1 base
T1 accepted HEAD → T2 base
T2 accepted HEAD → T3 base
...
```

Tn → Tn+1 前必須證明 ancestor 關係。不能跳回 X，也不能跳去兄弟鏈。

### I-05：整鏈完成前禁止合回 X

任何 child ticket、局部 GREEN、focused QA success 或單一 PR success 都不足以合回 X。

只有完整 Master Chain 的所有 required tasks 都 Task ACCEPTED，才可以進入 Integration Acceptance。

### I-06：Task Acceptance 與 Integration Acceptance 分離

**Task Acceptance** 回答：這條封閉鏈本身是否正確、完整、可重現、已通過要求的測試與 durable writeback。

**Integration Acceptance** 回答：這條已完成的 final chain HEAD 現在是否能安全整合進目前的 X。

兩者不得混成一個 gate。

### I-07：完成不等於自動 merge

完整 Master Chain 完成後，最低可到：

```text
ACCEPTED / READY_FOR_X_INTEGRATION
```

如果工單、使用者或 Master 明確寫了「先不要合回 X」，則必須停在這裡，等待明確授權；不得因為整鏈已 GREEN 就自動 merge。

## 4. 標準生命週期

### 4.1 建立 Master Chain

每條 A/B/C/D 都各自執行：

```text
READ X HEAD
  ↓
FREEZE FROZEN_X_BASE_SHA
  ↓
CREATE WORK_ORDER_BRANCH from exact SHA
  ↓
READ-BACK base identity
  ↓
CREATE/VERIFY Master Issue + child Issues
  ↓
START T0/T1...
```

最低必記：

- `MASTER_ID`
- `TARGET_X`
- `FROZEN_X_BASE_SHA`
- `WORK_ORDER_BRANCH`
- `WORK_ORDER_ACCEPTED_HEAD`
- `CURRENT_X_HEAD`（只做觀測）
- child issue lineage
- task state
- integration state

### 4.2 Child task 施工

每張 Tn 若需隔離，可從當下 `WORK_ORDER_ACCEPTED_HEAD` 建短命 implementation / QA branch。

驗收後只允許 non-force 收回本 Master 的 work-order branch，更新：

```text
WORK_ORDER_ACCEPTED_HEAD = Tn accepted HEAD
```

不得直接收回 X。

### 4.3 Master 完成

完整 Master 必須至少完成：

- 所有 child task terminal；
- required regression / Combined Acceptance；
- protected/config invariants；
- Skill / AI Library durable writeback；
- temporary QA/workflow cleanup；
- tested-head → closing-head drift audit；
- final chain HEAD sealed；
- owning Issues / Master evidence 回寫。

完成後標記：

```text
TASK_ACCEPTANCE = ACCEPTED
FINAL_CHAIN_HEAD = <sha>
```

### 4.4 Integration Readiness

以同一 frozen base 做三方比較：

```text
FROZEN_X_BASE_SHA → FINAL_CHAIN_HEAD
FROZEN_X_BASE_SHA → CURRENT_X_HEAD
FINAL_CHAIN_HEAD  ↔ CURRENT_X_HEAD
```

必須分類：

- source overlap；
- conflicts；
- behavior overlap；
- test/Skill/AI knowledge drift；
- config/protected-file drift；
- sibling chain 是否已先整合進 X。

若有真正衝突，建立 integration/hotfix task 處理；不得回頭污染原本 sealed chain history。

### 4.5 合回 X

只有同時滿足：

1. `TASK_ACCEPTANCE = ACCEPTED`；
2. `INTEGRATION_ACCEPTANCE = ACCEPTED`；
3. 使用者／Master 沒有 `DO_NOT_MERGE_X`；
4. 若有明確「完成後先不要合回 X」，已取得新的 explicit authorization；
5. current X identity 已再次反讀；
6. merge 是 non-force；
7. post-integration sentinel / regression 已有 owner。

才可以對 X 做一次整鏈 integration。

## 5. A/B/C/D 並行範例

```text
                    X @ S0
          ┌──────────┼──────────┬──────────┐
          │          │          │          │
      A chain     B chain     C chain     D chain
      base S0     base S0     base S0     base S0
          │          │          │          │
      A1→A2→A3    B1→B2      C1→C2→C3    D1
          │          │          │          │
      FINAL_A      FINAL_B      FINAL_C      FINAL_D
          │          │          │          │
    READY_FOR_X  READY_FOR_X  READY_FOR_X  READY_FOR_X
```

在 A/B/C/D active 期間，即使 X 從 S0 前進到 S5：

```text
X: S0 → S1 → S2 → S3 → S4 → S5
```

四條 active chain 的 parent lineage 仍從 S0 繼續，不允許把 S5 merge/rebase 進來。

若 A 完成並獲准先整合到 X，使 X 變成 S6，B 仍維持自己的原始 sealed lineage；B 完成後是在 Integration Acceptance 階段拿 FINAL_B 對 S6 做整合準備，不是把 S6 倒灌回 B 的已驗收 task chain。

## 6. Dispatch / Preflight / RUN Identity

每張 child ticket、checkpoint、QA dispatch 至少必須帶：

```text
MASTER_ID
TASK_ID
TARGET_X
FROZEN_X_BASE_SHA
EXPECTED_PARENT_SHA
WORK_ORDER_BRANCH
WORK_ORDER_ACCEPTED_HEAD / CHAIN_HEAD
CURRENT_X_HEAD (observation only)
```

Remote QA 另必須鎖：

```text
RUN_ID + HEAD_SHA + BRANCH
```

若尚未產生 RUN：狀態是 `RUN_NOT_CREATED`，禁止等待／輪詢不存在的 run；必須立即處理應產生 run 的 prerequisite。

## 7. Fail-Closed 條件

遇到下列任一情況，停止該 chain 的 production mutation並先修正 authority：

- frozen base 不明；
- child parent 不是上一個 accepted HEAD；
- branch 含兄弟 chain 未整合 change；
- active chain 被 merge/rebase 最新 X；
- RUN HEAD 不等於 claimed chain HEAD；
- evidence 來自其他 chain；
- integration 被誤當 task acceptance；
- partial task 被要求直接 merge X；
- current X drift 未分類；
- explicit `DO_NOT_MERGE_X` 仍存在。

## 8. 禁止事項

禁止以下合理化：

- 「X 已經更新，順便 rebase 比較乾淨。」
- 「B 的功能 A 也會用，先 cherry-pick 過來。」
- 「T3 已全綠，可以先 merge X。」
- 「A/B 都從 X 出發，所以 QA run 可以共用。」
- 「最後反正要合 X，現在先 merge X 進 chain 沒差。」
- 「整條鏈完成了，所以不需要再等使用者授權。」

以上全部視為治理違規。

## 9. Acceptance Checklist

### Master 建立

- [ ] X 已反讀。
- [ ] `FROZEN_X_BASE_SHA` 已記錄。
- [ ] Work-order branch 從 exact frozen SHA 建立並反讀。
- [ ] Master / child issue lineage 已建立。

### Active Chain

- [ ] child 只接 previous accepted HEAD。
- [ ] 未 merge/rebase current X。
- [ ] 未 import sibling chain production changes。
- [ ] task / branch / RUN identity 一致。

### Task Acceptance

- [ ] 所有 child terminal。
- [ ] Combined/final regression GREEN。
- [ ] Skill/AI knowledge durable writeback 完成。
- [ ] cleanup / invariant / drift audit 完成。
- [ ] final chain HEAD sealed。

### Integration Acceptance

- [ ] final chain vs current X divergence 已比較。
- [ ] conflicts / overlap / drift 已分類。
- [ ] integration result 可 non-force。
- [ ] `DO_NOT_MERGE_X` 已解除或取得 explicit authorization。
- [ ] post-integration owner / sentinel 已指定。

## 10. 對 Skill 的硬性要求

`.agents/skills/engineering/派工/SKILL.md` 必須永久包含與本規格一致的 `X_SECOND_MAIN_INDEPENDENT_CHAIN_CONTRACT`，至少覆蓋：

1. per-Master frozen X base；
2. A/B/C/D cross-chain isolation；
3. active chain 禁止 merge/rebase newer X；
4. child parent = previous accepted HEAD；
5. complete-chain-before-X；
6. Task Acceptance vs Integration Acceptance；
7. `READY_FOR_X_INTEGRATION` 不等於自動 merge；
8. explicit `DO_NOT_MERGE_X` 優先。

若 Skill 與本規格衝突，以使用者最新明確核准需求為最高 authority，並立即同步修正 Skill 與 AI Library，禁止只改其中一邊。
