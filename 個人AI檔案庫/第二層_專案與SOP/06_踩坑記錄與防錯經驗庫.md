# ⚠️ 06. 踩坑記錄與防錯經驗庫 (Bad Patterns & Lessons Learned)

> 本文件記錄 ㄚ凱 在 CAD/CAM、WHD 幾何展開與 Ollama 拆圖實戰中「踩過的坑」與「反面教材」。
> 所有 AI 在進行架構設計或代碼修改前，**必須先檢核本清單，嚴禁重蹈覆轍**。

## 🚫 幾何與演算法避坑指南

### 1. 視圖裁切範圍 (crop_bbox) vs 主箱體幾何範圍 (geometry_bbox) 混淆
- **踩坑情境**：將正視圖的裁圖範圍（含標註、PANEL 文字）直接拿來當成箱體實體幾何計算，導致幾何中心偏移（如 1385.27 vs 正確實體 1432.02）。
- **正確做法**：嚴格區分 `crop_bbox`（裁圖區）與 `geometry_bbox`（實體幾何），驗證尺寸只對準主幾何。

### 2. 箱體總高含底座導致展開尺寸錯誤
- **踩坑情境**：來源總外高為 2200（含 50mm 底座），若未扣除底座直接計算，會導致門板與箱身高度過大（如門算成 2161 而非正確 2111）。
- **正確做法**：使用 `detect_child_bottom_base()` 做幾何交叉驗證，確認底座後，箱體實際高扣除底座高，底座獨立輸出。

### 3. 硬編碼 12/16/17 點主外框陣列
- **踩坑情境**：為每個新零件手推頂點陣列，導致維護困難且無法通用。
- **正確做法**：全面使用 Shapely 布林運算（`Base Polygon - Relief Polygon`），新零件只需傳入折邊尺寸與扣量。

### 4. 任意把金庫型規則推廣為宇宙通則
- **踩坑情境**：直接將金庫型的 `0.5T` / `2T` 插入退讓套用到其他箱型（如戶外箱、落地盤）。
- **正確做法**：Topology（折彎結構）可共用，Factory Policy（退讓規則）必須依箱型獨立配置。


### 5. 把 `FW` 當成一般 Fold Segment，導致框寬被重新分配
- **踩坑情境**：箱身 `FW=25`，封頭／封尾旁邊另有 16mm 折邊；推導 arbitrary Fold Chain 時把兩者合併成 `16 + 25 = 41`，最後專案檔竟儲存成 `fw=41`，造成封頭尾與箱身門框基準失去一致。
- **根本原因**：混淆「成品框寬尺寸語意」與「展開折彎鏈 segment/span」。
- **正確做法**：`FW` 永遠是邊框寬度／框寬的獨立 Source of Truth；Fold Chain 可以引用 FW，但不得重新分配、合併後再冒充 FW。相鄰的 16mm、15mm 等折邊必須保留自己的語意。

### 6. 把 2D 展開 `bbox` 當成 3D 折後包外尺寸
- **踩坑情境**：箱身 2D 展開 material bounds 為約 `938 × 596`，3D 尺寸標註直接沿用該範圍，導致把展開寬 938 誤標成成品寬；或直接用 core `396 / 246` 當成成品 `W / D`。
- **根本原因**：未區分「展開板尺寸」、「core 尺寸」、「單件折後包外」與「整箱組裝包外」四種不同尺寸空間。
- **正確做法**：3D 尺寸從折後實際外表面 envelope 計算並包含板厚；單件視圖標單件折後包外，整箱視圖標組裝後 `W / H / D`。

### 7. 忽略組合方式，錯把箱身單件高度永遠等同整箱 `H`
- **踩坑情境**：設定箱體 `H=600, T=2` 時，不論封頭／封尾是嵌入、貼外或嵌入貼外，都把箱身單件高度硬寫成 600；或反過來看到箱身 596 就誤認整箱成品高只有 596。
- **根本原因**：混淆「完整箱體包外 H」與「箱身單件折後高度」，沒有把封頭／封尾在外部占用的板厚納入尺寸鏈。
- **正確做法**：`INSERT=0T`、`OVERLAY=1T`、`INSERT_OVERLAY=1T`（每一端）。`BoxBodyFinishedHeight = H - HeadOutsideOccupancy - TailOutsideOccupancy`；完整組裝後仍回到輸入 `H`。下方 `CROSS / extra_cut` 不參與此高度扣量。

### 8. 封頭／封尾各自保存一份折法，與箱身 Fold Chain 漂移
- **踩坑情境**：箱身由 9 段改為 5 段後，專案檔仍保留舊封頭／封尾 profile；3D、2D、DXF 甚至可能各自看到不同 BEND 數量。
- **根本原因**：把 derived end-cap mating profile 當成與箱身同等的獨立 Source of Truth。
- **正確做法**：箱身 Fold Chain 為折法權威來源；封頭／封尾接合 profile 依箱身拓撲、FW 與組合方式即時推導。按「確定」後同一份狀態必須回到 2D 與 DXF。

### 9. 用固定段數判斷 Fold Chain
- **踩坑情境**：為 5 段、9 段各寫一套 if/else，新增 6、7、12、20 段時立刻失效。
- **根本原因**：把實例的段數誤當成拓撲規格。
- **正確做法**：以 ordered Fold Chain + semantic dimensions/core/assembly policy 驅動；測試可覆蓋 3/5/9/12/20 段，但 production code 不得依賴固定段數。

### 10. 板件「刪除」只做 UI 隱藏或要求先進入板件頁
- **踩坑情境**：沒有的板件必須先切進該頁才可刪除，或畫面看似刪除但 `existing_parts`、2D tab、DXF export、`.p6fold` 仍把它當存在。
- **根本原因**：把「目前選中頁面」與「板件存在狀態」綁在一起。
- **正確做法**：板件選擇區選中即可刪除；`existing_parts` 是正式狀態並同步 2D/3D/export/project。箱身為主體不可刪；其他板件可刪除與加回。

### 11. 把 FW 連動做成「永久鎖死」或「兩端各自 override」
- **踩坑情境**：為避免 FW 漂移，直接把封頭／封尾 FW 欄位設成唯讀；或反過來讓封頭、封尾一開始就各自獨立 override，導致實際操作時無法符合「先改一端就帶另一端、再改另一端才分離」的習慣。
- **根本原因**：只用兩個 `follow_box` 布林值描述控制權，無法表達「箱身主導 → 封頭主導／封尾主導 → 兩端獨立」的操作歷程。
- **正確做法**：使用四態 `FOLLOW_BODY / FOLLOW_HEAD / FOLLOW_TAIL / INDEPENDENT`。初始箱身主導；先改封頭則封尾跟封頭，先改封尾則封頭跟封尾；之後再改原 follower 才解除連動。任何狀態下，只要使用者重新提交箱身 FW（即使同值），箱身立即重新接管兩端。
- **UI 要求**：封頭／封尾 FW 欄位保持可直接輸入，不靠 disabled/readonly 來維持資料一致性；一般 redraw/refresh 不得偷偷切換控制權。
- **一致性要求**：2D、3D、CornerPolicy、FinalScene、DXF export、`.p6fold` 必須使用同一個有效 FW 解析結果，禁止 UI 顯示一套、加工端使用另一套。

### 12. 箱身已刪外側折，封頭／封尾卻仍硬補舊折段
- **踩坑情境**：箱身 Fold Chain 從原本較多段改成 `FW → D → W → D → FW` 後，封頭／封尾 2D 仍保留舊 `ytop1=16` 類外側折，使用者必須手動刪掉才看起來正確。
- **根本原因**：end-cap derivation 把舊固定 profile 當 fallback，而不是把「該折段是否存在」直接由箱身 topology 決定。
- **正確做法**：箱身刪折就自動刪除封頭／封尾對應折；新增/改角度亦同步。可選 segment 缺席是合法狀態，不得自行補回 legacy fold。

### 13. 只刪 BEND，沒有同步縮短 2D blank / material 外框
- **踩坑情境**：封頭／封尾視覺上少了一條 BEND，但 2D 外框仍沿用舊 fold_top 尺寸，導致板件尺寸沒有真正跟箱身對齊。
- **根本原因**：BEND profile 與 Base Polygon / structural dimensions 分開計算，形成兩套幾何。
- **正確做法**：Fold Profile 改變時，BEND、Base Polygon、material bounds、blank size 與 DXF 必須從同一份 derived profile 一次重建。

### 14. 沒有 `angle` 的 boundary 仍被畫成 BEND，造成 2D/3D 分叉
- **踩坑情境**：2D 因 cumulative boundary 存在而畫出一條 BEND，但該 segment 沒有 angle；3D 因沒有 angle 不會折，最後出現「2D 有折線、3D 卻共線 180°」的怪圖。
- **根本原因**：BEND 生成只看 segment 邊界，不看是否真的存在折彎指令。
- **正確做法**：只有明確具 `angle` 的 segment boundary 才能生成 BEND；Final 2D BEND 與 3D fold 必須 1:1。90° 是否正確要直接驗證相鄰折後面的夾角。

### 15. 封尾 native order 反轉時遺失／錯置折彎角度
- **踩坑情境**：封尾本身沒有被使用者修改，但反向 profile 中某個 FW segment 失去 angle，造成最後兩段折後共線或折向錯誤。
- **根本原因**：直接拿已經 native/reversed 的 tail profile 再當 canonical 模板，反轉 segment 順序時沒有保留「angle 屬於哪一道 boundary」的語意。
- **正確做法**：先從箱身建立 canonical mating chain，再轉換成封頭/封尾 local/native order；轉換時以 bend boundary 為單位搬移 angle，不以 list index 或 terminal segment 猜測。

### 16. 合法缺少可選折段，reader 卻判成「資料不完整」並 fallback 舊幾何
- **踩坑情境**：2D 已正確刪除 `ytop1` 對應折段，但 3D payload reader 因找不到 `ytop1` 就拋錯，最後退回舊固定 profile，造成 2D 正確、3D 又回到舊尺寸／舊 BEND。
- **根本原因**：把 legacy 固定欄位當成必要欄位，沒有支援任意 topology 的「segment 可以不存在」。
- **正確做法**：缺少可選 segment 應解析為 absent/0，而不是資料損壞；3D 必須直接使用同一 FinalScene / derived profile，不得 silent fallback 成舊 topology。

## 💻 程式開發與環境避坑指南

### 1. 硬編碼絕對路徑或暫存目錄
- **踩坑情境**：程式中寫死 `C:/Users/looae/.../my_debug.txt` 或固定輸出至特定專案目錄，換環境即崩潰。
- **正確做法**：輸出路徑一律跟隨使用者在 GUI 指定的「輸出根目錄」；臨時檔案放 `tmp/`。

### 2. 測試斷言未經真圖/真 CSV 驗證
- **踩坑情境**：單靠腦補或修改測試碼讓它表面通過，實際上線處理真實 DXF 時出錯。
- **正確做法**：嚴格遵守 TDD，先跑真圖 regression，確認尺寸與 DXF 圖元無誤。

### 3. 未備份直接覆寫目標檔案
- **踩坑情境**：手滑改錯造成原始圖檔或關鍵代碼損壞。
- **正確做法**：修改前必須強制備份至 `BACKUP/YYYYMMDD-HHMMSS-檔名`。

### 4. 程式已改規則，卻等使用者再次提醒才更新 SOP
- **踩坑情境**：程式已新增/修正幾何、資料契約或 UI 行為，但規範仍停留在舊版本；後續 AI 讀到舊 SOP 又把已修好的行為改回去，或使用者必須重複提醒「把這條寫進文件」。
- **根本原因**：把文件更新當成額外任務，而不是程式修改的完成條件。
- **正確做法**：凡新增/修改正式行為或解掉可重現 Bug，本輪交付時直接同步對應 SOP 與本踩坑庫；**不等待使用者再次要求**。程式、測試、README/SOP 必須同版。

### 17. 為避免 ZIP 中文問題擅自把原始檔名改成 ASCII
- **踩坑情境**：遇到 Windows / ZIP 中文 entry 相容性問題時，為求方便把 `04_WHD鈑金展開幾何引擎規範.md` 等使用者原始檔名改成英文 ASCII 名稱，導致檔案庫結構與使用者既有命名不一致。
- **根本原因**：把「封裝／編碼問題」錯當成「檔名問題」，用改名規避真正的 UTF-8/ZIP 相容性問題。
- **正確做法**：保留原始中文檔名與資料夾結構；ZIP entry 明確使用 UTF-8，完成後實際解壓並逐檔比對 SHA256。只有使用者明確要求時才重新命名。

### 18. 封頭／封尾折角被硬寫成 90°，忽略 Fold Chain 輸入
- **踩坑情境**：箱身 Fold Chain 已輸入 45°、60° 或其他角度，但 linked EndCap derivation 只因「常見鈑金折彎」就把所有 angle 強制改成 `-90`，導致 3D 與操作員輸入不一致。
- **根本原因**：把「常見預設值」誤當成「製造規則」，derived topology 越權改寫 angle。
- **正確做法**：輸入幾度就折幾度；derived profile 只搬移 bend boundary 的 angle ownership，不得重設 angle magnitude/value。UI/engine 內部表示轉換必須 round-trip 無損。

### 19. 用相機投影設定掩蓋折彎角度 Bug
- **踩坑情境**：3D 看起來不像直角時，先改成 orthographic projection，希望畫面「看起來比較 90°」，但真正 Fold Chain/derived angle 仍然錯。
- **根本原因**：混淆 view/render policy 與 geometry。
- **正確做法**：視角只管顯示；角度只由 Fold Chain 輸入與折彎幾何決定。除非是獨立的顯示需求，不得修改 projection 來修幾何問題。

### 20. Phase6 已 commit 正確 FinalScene，主 2D 卻變成 `-` 或仍顯示舊尺寸
- **踩坑情境**：Phase6 封頭／封尾已是新 profile，但主 GUI `update_calculations()` 某分支沒有初始化後續共用變數，例外又被最外層 catch 吃掉，結果所有尺寸顯示 `-`；或仍走 legacy 尺寸公式。
- **根本原因**：主 2D 沒有完全沿用 committed FinalScene，且 silent exception 隱藏資料鏈斷點。
- **正確做法**：commit 後主 2D 尺寸直接量 authoritative RenderData/FinalScene；共用狀態在分支前初始化，真檔 GUI regression 必須驗證實際顯示值而不只 helper。

### 21. 板件按鈕要求雙擊／再按編輯，刪除動作位置不符合操作流程
- **踩坑情境**：單擊只選中，還要雙擊或再按一次「編輯」才進板件；刪除按鈕又藏在板件頁內，增加不必要操作。
- **根本原因**：把 selection 與 navigation 過度拆開，沒有依實際操作習慣設計。
- **正確做法**：板件按鈕**單擊一次直接進入**；不另設 Edit。刪除按鈕固定在板件按鈕區下方，箱身 disabled，其餘板件依存在狀態啟用。
### 22. AI 把「沒有重新驗證」誤判成「已確認機械規則可能是錯的」
- **錯誤現象**：使用者指出 AI 其實沒有真正理解「箱身＋封頭／封尾」組合關係後，AI 雖然正確承認先前有瞎猜，但接著又過度修正，把下列已經確認的正確規則一起說成「應撤回、不能當已知事實」：
  1. 箱身刪除組合接合鏈上的外側一折時，封頭／封尾對應折也要同步刪除。
  2. 封頭／封尾上方截角本身就是組合方式／裝配語意。
  3. 貼外關係每端占用 `1T`：`INSERT=0T`、`OVERLAY=1T`、`INSERT_OVERLAY=1T`。
  4. 五段箱身 `FW-D-W-D-FW` 時，封頭為 `FW-D-後折`，封尾 native orientation 為 `後折-D-FW`，不得補回舊 `ytop1` 外側折。
- **這次 AI 犯的真正錯誤**：
  - 把「我之前沒有親自重新證明這條」偷換成「這條本身可能是錯的」。
  - 看到程式存在 `assembly_type`，就武斷解讀成它和上方 CornerType 是兩套互相競爭的機械真值，沒有先確認它是否只是 UI／保存／映射層。
  - 因為 ZIP 當下沒有真 DXF／實體案例，就錯誤認為不能維持先前已由使用者確認的機械規則。
  - 一度想用「目前程式怎麼寫、測試怎麼斷言」來反推機械關係，形成循環論證：AI 猜規則 → 規則被寫進程式／測試 → AI 再拿程式／測試證明自己的猜法。
  - 沒有先區分「已確認的機械真值」「目前實作」「AI 尚未理解的部分」三個層次。
- **正確理解**：
  - 上述四條是使用者已確認的箱身 ↔ 封頭／封尾組合基準，後續檢查程式要問的是「哪裡沒有遵守」，不是再把四條拿回來猜一次。
  - 「箱身刪一折」必須精確限定在**組合接合鏈的外側可選折**，不能擴張成 D-W-D 核心也可隨意刪除。
  - 上方 CornerType 是機械裝配語意；額外欄位若存在，必須確認只是 representation / persistence，不得先假定為第二套真值。
  - `OVERLAY` 與 `INSERT_OVERLAY` 每端都占 `1T`；箱身單件高度據此從完整箱高 `H` 扣除，但完整組裝包外仍回到 `H`。
  - 5 段箱身的 end-cap mating profile 不得重新長回已被箱身 topology 刪除的 legacy 外側折。
- **防錯規則**：
  1. 使用者已明確確認並固化的機械關係，優先級高於目前程式、測試與舊設計文件。
  2. 缺少新證據只代表「不能再新增推論」，不代表「既有已確認規則失效」。
  3. 程式與規則衝突時，先把程式列為嫌疑對象，沿 Source of Truth → derived profile → FinalScene → 2D/3D/DXF 追資料流。
  4. 只有出現新的直接幾何證據、現場裝配證據或使用者明確更正，才可以提出修改既有機械基準。
  5. 測試通過只能證明「程式符合測試」，不能單獨證明「測試所描述的機械關係真實」。


### 23. AI 把封頭／封尾誤想成箱身「前後折」或單側 Fold Chain 的延伸
- **錯誤現象**：在討論箱身兩側外加折數不對稱時，AI 先問「封頭尾到底跟左邊還是右邊」，甚至把 Head/Tail 想成箱身前後兩側 Fold Chain 的延伸，試圖用單一 `source_front` / canonical chain 解釋整片端板。
- **根本原因**：只盯著 2D 一維 Fold Chain 與陣列順序，沒有先在腦中完成箱身折起後的實體拓撲。`FW-D-W-D-FW` 折起後形成的是背面 `W` + 左右側面 `D`，兩個 `FW` 是正面框邊；真正留下的是正面、上端、下端三個開口。
- **正確理解**：門補正面開口；封頭補上端開口；封尾補下端開口。封頭／封尾是上下端板，不是箱身前折／後折，也不能直接等同箱身某一側 Fold Chain。
- **防錯規則**：
  1. 遇到箱體組合問題，先畫出／描述折後實體的面與開口，再談 2D segment 對應。
  2. 不得由 `rows[:first_D]`、list 左右順序或「front/back」變數名稱直接推斷物理接合關係。
  3. 當左右外加折數不相同時，**在使用者確認前不要回答『跟誰』**；必須保留為待確認機械映射問題。
  4. 不得為了讓現有 helper 看起來合理，就把整個端口四周關係降維成一條 chain。

### 24. `assembly_type` 反向覆寫上方 CornerType，形成第二套機械真值
- **錯誤現象**：資料同時存在 `assembly_type` 與 Head/Tail 上方 CornerType 時，載入流程若優先相信 `assembly_type`，會把原本的上方 CornerType 改掉，連帶造成 2D 截角／組合語意被改寫。
- **根本原因**：把方便 UI／保存的 mirror 欄位提升成 Source of Truth。
- **正確理解**：封頭／封尾上方 CornerType 本身就是組合方式的機械語意；`assembly_type` 若保留，只能是 mirror/compatibility state。
- **防錯規則**：載入時不得以 `assembly_type` 覆寫上方 CornerType；不一致時以上方 CornerType 為準並同步 mirror，或明確報資料不一致。任何 2D 截角生成也必須直接消費 authoritative CornerType。

### 25. 用展開圖左右／折數直接猜封頭尾要跟誰
- **錯誤現象**：面對箱身一側 FW 外多 2 折、另一側多 1 折時，AI 直接回答「左側跟左側、右側跟右側」，或想以 segment 數量決定封頭／封尾對應。
- **根本原因**：仍把 2D Fold Chain 當成機械接合本體，沒有先判斷每一道 Fold 折起後的實體形態。
- **正確理解**：是否需要由封頭／封尾跟隨，必須看折後形態：該段最後落在哪個面、折向、是否形成上／下端口邊界、是否實際與端板搭接／包覆／嵌入。『跟誰』是折後形態分析的結果，不是用左右位置或折數先決定的規則。
- **目前範圍決策**：依折後形態會衍生多個新接合型態，使用者目前明確暫不處理。程式不得先發明新型態或猜配對；先只修既有 `assembly_type` 覆寫 Top CornerType 的資料真值 Bug。
- **防錯規則**：看到非對稱 Fold Chain 時，先標示為尚未建模的形態問題；除非已有使用者確認的形態分類，不得自動衍生 EndCap mapping。

### 26. 組合方式 Combobox 在自己的選擇事件中被重建，造成整頁／控制項消失
- **錯誤現象**：使用者在箱身選擇 `INSERT / OVERLAY / INSERT_OVERLAY` 後，組合方式控制或整個設定頁突然消失。
- **根本原因**：`<<ComboboxSelected>>` callback 裡立即 invalidate + destroy/rebuild 目前 box_body page，Tk 還在 dispatch 原 widget 的事件時就把來源 widget 銷毀。
- **正確做法**：目前 box_body page 保持存活；只 invalidate 依賴組合結果的 Head/Tail cache，derived geometry 即時更新，Head/Tail 等使用者切入時再重建。

### 27. 自訂模式雖隱藏「基準檔開孔資料」，卻又從進階設定把固定孔資料露回來
- **錯誤現象**：選 `自訂` 後表面上沒有基準檔區，但封頭／封尾「進階設定」仍出現掛孔、固定方孔、封尾固定孔等基準檔欄位。
- **根本原因**：同一 Setting group 同時被分類為 baseline-only 與 advanced，UI 分類重疊。
- **正確做法**：`固定孔 / 封尾固定孔` 只能屬於 baseline-only；自訂模式整組不存在，且不得進 advanced_specs。

### 28. 對稱折彎只同步輸入值，刪除卻只刪單側
- **錯誤現象**：勾選「對稱折彎」後改長度／角度會鏡像，但刪折段仍只刪點到的一側，箱身立即變成非對稱。
- **根本原因**：remove path 沒走既有 mirror mapping，只做單一 `pop(idx)`。
- **正確做法**：對稱箱身刪除使用同一 mirror index 規則；先確認兩側都可刪，再由高 index 到低 index 同一交易刪除。任一側不可刪則全部不動。

### 29. 3D draft 與主 2D 可同時編輯，造成 committed state 競爭
- **錯誤現象**：3D Fold Designer 開著時，主 GUI 2D 仍可修改；之後按 3D「確定」可能用較舊 draft 覆蓋剛在 2D 做的修改。
- **根本原因**：3D Toplevel 只是普通視窗，沒有建立 modal transaction 邊界。
- **正確做法**：3D 開啟期間以 modal grab 鎖住主 2D；確定才提交 draft，取消/X 丟棄並釋放 grab。禁止用兩邊同步寫入來掩蓋競爭。

### 30. 把 `OVERLAY` 只當 Corner relief 差異，忘了貼外型本身沒有左右 X 折彎
- **錯誤現象**：選貼外後，封頭／封尾 2D/3D 還保留左右折線，X 軸 Fold editor 也仍可編輯不存在的折彎，因此圖形明顯不符合實際貼外形態。
- **根本原因**：只換 Top CornerType/切口公式，卻沿用 `yl1 - W-core - yr1` 的有折 X profile。
- **正確做法**：`OVERLAY` 的 EndCap X profile 從資料源即表達為無 angle 的 flat span；FinalScene 不得產生 X BEND，3D Fold editor 隱藏 X 軸折彎頁。2D、3D、DXF 必須由同一 topology 得到相同結果。

### 31. 把既有 `CROSS + EXTRA_CUT` 能力誤判成「需要新增 1.5T CornerType」
- **錯誤現象**：AI 看到 `OVERLAY` 沒有左右 X 折彎，就認為十字多切不能用，進而主張為 1.5T 另外新增 CornerType；或把「不能直接改全域 0.5T」誤解成「現有模型無法表示 1.5T」。
- **根本原因**：混淆了 `CornerType`、`cross_mode`、`direction`、`amount_t` 四個層級，也把「多切的幾何手段」和「為什麼需要避讓的機械目的」綁成同一件事。
- **正確理解**：`CROSS + EXTRA_CUT` 本來就能選 `WIDTH / HEIGHT / BOTH`，`amount_t` 也可為任意正值。即使 X Fold 基底為 0，`WIDTH + 1.5T` 仍可合法形成 1.5T 寬向避讓，不需新增 CornerType。
- **OVERLAY 已確認預設**：使用者明確選擇貼外型時，封頭／封尾下方初始帶 `CROSS + EXTRA_CUT + WIDTH + 1.5T`；這只在明確切換組合方式時套用。後續人工修改下方方向／amount 後，普通刷新不可洗回預設。
- **防錯規則**：不得把全域舊預設 `C03 = BOTH + 0.5T` 改成 1.5T；也不得看到另一板金干涉就發明新 CornerType。先確認現有 `CROSS` 參數是否已能精確表達所需幾何。
### 32. 只刪 `OVERLAY` 的 X BEND，卻保留 INSERT 型 422 材料外框
- **錯誤現象**：貼外封頭／封尾畫面看起來已沒有左右 X 折線，Fold editor 也只剩 Y，但主 2D／FinalScene 展開寬仍顯示 `422`（例如 `W=400, T=2, yl1=yr1=15`）。
- **根因**：Bridge 先用舊 INSERT 型 `15 + (W-4T) + 15 = 422` 建 X profile，再只是把三段壓成一段無 angle 的 flat profile；同時 AE `build_unknown_endcap_result()` 的 structural blank 仍用 `W-4T+|yl1|+|yr1|`。也就是 BEND topology 改了，但 CUTTING/material topology 沒改。
- **正確做法**：`OVERLAY` 上方 CornerType 已表示封頭／封尾無左右 X 折彎，因此 X structural blank 必須直接使用 `W`，`left_fold/right_fold=0`，且 structural bends 不得包含 `left/right`。Bridge 的 `endcap_w_flat` 同樣直接取 `W`。
- **重要邊界**：下方 `CROSS + EXTRA_CUT + WIDTH + 1.5T` 是局部角落避讓，不能拿來加減整張封頭／封尾材料寬度。
- **真檔回歸**：`自訂(4).p6fold` 保存了舊 workspace `endcap_w_flat=422`；載入後必須依現在的 OVERLAY topology 重建為 `400`，Head/Tail FinalScene material bounds 為 `400 × 284`。

### 33. 截角縮圖只做全域翻轉，沒有區分上方／下方
- **錯誤現象**：先前為符合操作視角，把所有 CornerType 小圖一起垂直翻轉；當使用者切到下方截角時，小圖方向反而與下方實體閱讀方向相反。
- **根因**：preview transform 沒有接收目前 active corner target，只存在單一全域 Y 翻轉。
- **正確做法**：上方／左上／右上維持翻轉；下方／左下／右下恢復原始方向。小型 CornerType 選擇圖與大型預覽必須使用同一 target orientation。此改動只屬 UI。

### 34. UI 直接輸出 float，讓 `400` 顯示成 `400.0000000000006`
- **錯誤現象**：幾何意義是 400mm，但某些 UI formatter 以 `is_integer()` 精確比較後直接 `str(float)`，因此把二進位浮點尾差完整顯示。
- **根因**：把浮點表示誤差當成有效尺寸差異。
- **正確做法**：只在顯示層以極小容差判定近整數；近整數顯示整數，合法小數保持原值。禁止用顯示需求反向 round 製造幾何或 DXF。


### 35. 刪掉板件只藏 3D／右側 Tab，左側結果與輸出仍殘留
- **錯誤現象**：3D 已刪除 Door/底板等板件，主 GUI 右側 tab 可能已隱藏，但左側「展開尺寸計算結果」仍顯示該板件列、佔空間；輸出零件 checkbox 也仍留著。更危險的是，stashed `part_profiles` 或 stale checkbox 還可能讓不存在板件被重新計算／輸出。
- **根本原因**：只把 `existing_parts` 當成某一個 UI 元件的顯示條件，沒有把它提升成全鏈 physical presence Source of Truth；同時把「是否勾選 DXF」錯當成「板件是否存在」。
- **正確做法**：physical presence 與 export selection 分離。所有 2D/3D UI、結果計算、FinalScene、保存/重載、DXF/NC/批次輸出都先檢查同一份 `existing_parts`；不存在的 UI 元件用 `pack_forget`/hidden 完整移除，不留下空白。stashed profile 只供重新新增恢復，不得觸發 Scene/輸出。
- **防錯驗證**：至少要有三類 regression：不存在板件零佔位；stale checkbox=True 仍不能輸出；stashed profile 存在但 physical presence=false 時不得建 FinalScene。

### 36. 有存檔核心卻沒有讀檔 UI 入口
- **錯誤現象**：3D Fold Designer 右下已有「存檔」可輸出 `.p6fold`，程式核心也已有 `load_phase6_project()`、argv／雙擊副檔名載入能力，但工作區沒有「讀檔」按鈕，使用者在程式內形成「能存不能讀」的操作斷鏈。
- **根本原因**：只驗證 persistence backend，沒有把成對的使用流程（Save / Load）列入同一條驗收鏈。
- **後續更正後的正確做法**：`.p6fold` 是全專案檔，入口應放在主視窗左上角全域 `開啟專案 / 儲存專案 / 另存新檔`；3D Footer 不再承擔專案檔讀／存。所有入口仍共用主 GUI authoritative `load_phase6_project()`／project writer。
- **全鏈要求**：讀檔後 `W/H/D/T/FW`、CornerType、Fold profiles、holes/features、`existing_parts`、2D/3D、輸出選項與 active part 必須來自同一份 snapshot。不得只把檔案讀進記憶體卻漏刷新 UI，亦不得讓刪除板件因舊 checkbox/profile stash 復活。
- **Windows EXE**：`.p6fold` 雙擊開檔與 UI「讀檔」共用同一 authoritative loader；兩種入口不得分叉成兩套還原邏輯。


### 37. 只讓已知盤型 UI 可解鎖，卻沒有把人工參數送完整製造鏈
- **錯誤現象**：已知盤型畫面可以解鎖修改截角細參數，但存檔 snapshot 又用 `known_model_corner_state()` 重建 factory 值，或 PartSpec/manufacturing 只在自訂盤型傳 corner policy，造成「畫面改得到，存檔／2D／3D／DXF 不一定真的用」。
- **根因**：把「可編輯 UI」當成需求終點，沒有沿 Source of Truth → Save/Load → PartSpec → baseline manufacturing 追完整鏈。
- **正確做法**：已知盤型 type_id 固定，只允許同 type 細參數覆寫；實際 `manual_corner_state` 必須序列化並傳到底。baseline DXF 優先，corner policy 只換 structural outline/BEND，固定孔與 MARKING 保留。
- **防錯**：需要 known-model round-trip 測試與 baseline secondary-feature regression，不能只測 input state。

### 38. 把全專案 Save/Load 放進某一個板件／3D Footer
- **錯誤現象**：功能本身能讀寫 `.p6fold`，但按鈕綁在 Fold Designer Footer，造成專案層級能力看起來像 3D 頁面的局部功能，也讓其他頁面操作不對稱。
- **根因**：UI scope 與資料 scope 不一致；`.p6fold` 保存的是整個 project state，卻把入口放進 part-level transaction。
- **正確做法**：主視窗左上角全域提供 `開啟專案 / 儲存專案 / 另存新檔`；因 3D 是 modal、主視窗此時不能按，所以 3D 視窗左上也提供同一組全域入口。3D Footer 只留板件 `確定 / 取消`。雙擊 `.p6fold` 與 GUI/3D 開啟共用同一 loader。

### 39. 測到「鎖定 flag」卻沒測到使用者真的看到鎖、參數真的消失
- **錯誤現象**：自動測試顯示 `_corner_param_unlocked=False`，細部 entry 的某個 frame 也被隱藏，但實際畫面仍攤著大部分上/下、左右相同等編輯控制；鎖按鈕只顯示不明顯的圖示/短文字，使用者感受就是「沒有鎖也沒有隱藏」。
- **根因**：把 state test 當成 visual/layout 驗收，只檢查 helper boolean / widget object，沒有檢查實際 geometry manager 與零佔位。
- **正確做法**：2D 與 3D 鎖定時都必須顯示明確 `參數鎖定` 文字；細部參數 frame、`左右相同` 等進階控制實際 `pack_forget/grid_remove`。解鎖才重新顯示；CornerType 類型/摘要仍可保留辨識。
- **防錯驗證**：Tk regression 必須 assert 鎖鈕 `winfo_manager()` 有值、細節容器鎖定時 `winfo_manager()==''`、解鎖後恢復；不能只測內部 dict。

### 40. 3D draft 與 committed 靠 callback 默契維持，讓全域 Save 可把未確定草稿寫進專案
- **錯誤現象**：主 GUI 原本 W=400，開啟 3D 後把 staged W 改成 500，尚未按「確定」就從 3D 執行「另存新檔」；舊 Bridge 會直接序列化自己的 staged workspace，結果 `.p6fold` 被寫成 W=500。取消 3D 後畫面雖回 400，但檔案已被未確認草稿污染。
- **根本原因**：專案交易所有權分散在 `_phase6_loaded_project_path`、`fold_designer_part_bundle`、`_phase6_existing_parts`、`_fold_designer_last_part_key` 與 Bridge `_phase6_input_snapshot`；「取消就是不呼叫 commit」只是 caller 默契，沒有一個 deep module 能回答目前哪份資料才是 loaded baseline、committed、draft。
- **正確做法**：新增純 Python `ProjectSession`，正式擁有 `project_path / loaded_baseline / committed / draft` 交易生命週期；所有 snapshot crossing interface 做 defensive deepcopy。main-connected 3D project save 一律回委 main GUI，以 `snapshot_for_save()` 保存 committed；active draft 期間 `capture_committed()` 必須拒絕，防止 caller 偷繞過 transaction。
- **3D 編輯邊界**：ProjectSession 的 draft 是隔離種子／交易生命週期，不是每次 Tk 修改都同步的第二份 live state。Fold Designer 編輯自己的 defensive copy；「取消」丟棄 transaction，「確定」先把 payload 套回 main GUI，再以 canonical main snapshot `commit_draft()`。
- **導航 metadata 例外**：既有回歸要求 3D 全域 Save 可記住目前 `active_part`。這不是機械狀態，因此可當 `active_part_hint` 寫入輸出 payload，但只接受已存在於 committed `existing_parts` 的板件；不得藉此提交 draft 新增板件、尺寸、CornerType、Fold Profile 或 features。
- **執行期欄位**：`_runtime_project_path` 只用來讓 3D 知道目前檔案路徑，不能跟著 canonical snapshot 寫入 `.p6fold`。
- **防錯測試**：至少鎖住四條：draft 500 + Cancel → committed 400；draft 500 + Confirm → committed 500；draft 500 + Save → file 400；active draft 時直接 `capture_committed()` 必須拒絕。另驗證既有 committed 板件的 `active_part` 可保存，但未 committed 新板件不能偷渡。

### 41. 把「儲存為預設值」誤當成「提交目前 Runtime」，讓 3D draft 偷改 AE
- **錯誤現象**：主 GUI committed W=400，進 3D 把 draft W 改成 500，尚未按「確定」先按「儲存為預設值」。舊 `save_defaults_to_ini()` 會同時寫 `config.ini` 與呼叫 `apply_settings_to_ae()`，結果 INI=500、AE.W=500；之後即使取消 3D，主 GUI／ProjectSession 仍是 400，但 AE compatibility globals 已漂移成 500，造成不同下游可能各拿到不同答案。
- **根本原因**：把「持久化給下次啟動」和「提交目前 Runtime」綁成同一個 helper side effect；同時 GUI `_settings_state`、Tk vars、AE globals、INI 都可能被當成 current settings owner。
- **正確做法**：`SettingsService` 是 committed runtime 唯一所有者。`update()` 只更新 service + AE compatibility mirror，不寫 INI；`persist_defaults()` 只寫 persisted defaults，不更新 service/AE；`Phase6Settings` 以 immutable/defensive snapshot 跨 interface。
- **3D transaction**：Fold Designer `_settings_values` 是合法 draft，不必消滅。Cancel 不呼叫 committed update；Confirm 才把 payload 套回 main GUI 並經 service commit。「儲存為預設值」可保存 draft 給下次啟動，但不可等同 Confirm。
- **Factory Defaults**：`ae.default_config` 是「還原初始值」來源；不能拿 persisted INI 或目前 service snapshot 假裝 Factory Defaults。
- **相容層**：AE module globals 可暫時保留，但只能作 service 同步出的 compatibility mirror。低階 `save_defaults_to_ini(..., apply_runtime=True)` 只供舊 caller 相容，新 production path 必須經 service。
- **防錯測試**：至少同時斷言 service / AE / INI 三者：runtime update → service/AE 改、INI 不改；persist draft → INI 改、service/AE 不改；3D Cancel → committed/AE 不變；3D Confirm → committed/AE 一起更新；新 service 啟動才讀取新 persisted defaults。


### 42. 把 Controller 化做成「搬方法到新檔」，結果 caller 還是得知道交易順序
- **錯誤現象**：看似新增了 `Controller`，但 GUI 仍要自己判斷 `has_draft`、決定何時 `capture_committed()`、何時 `snapshot_for_save()`、何時更新 path；新類別只是把原方法包一層，刪掉它幾乎沒有複雜度回到 caller，是典型 shallow module / Middle Man。

- **防錯測試**：至少鎖住 active draft 不呼叫 provider、非法 `active_part_hint` 不生效、load 取代 draft、confirm 提交 canonical snapshot、writer failure 不改 path，以及 GUI 不再直接呼叫 ProjectSession ordering / project read-write。

### 42. 把 Workspace Controller 做成舊 dict 的包裝，或載入新專案時保留上一個 Fold Chain
- **錯誤現象**：表面新增了 Controller，但 `gui.py` 還直接讀寫 `fold_designer_part_bundle / _phase6_existing_parts / _fold_designer_last_part_key / fold_designer_box_body_profile`，實際 Source of Truth 仍散在 caller；另一種更危險的情況是先載入有 `box_body_profile` 的專案，再載入沒有 profile 的專案，舊 Fold Chain 仍留在主 2D/3D 計算中。

- **防錯測試**：至少鎖住 mandatory box_body、authoritative presence 不受 export/indicator fallback 影響、刪除/重加 profile stash、active fallback、defensive copy、跨專案載入清除 stale Fold Chain、GUI production 不再依賴 legacy aliases。

### 48. 統一開孔編輯器把 Undo／取消／context snapshot 留在 Tk 巢狀函式，造成同一孔位有多套交易狀態

### 50. 先用截角公式猜 Assembly Relief，沒有從真實 Collision Region 反推 CUTTING

### 59. 固定截角診斷拿整片 EndCap 做碰撞，會把正常接合縫誤報成整圈干涉
- **錯誤現象**：標準金庫型補回固定截角後，早期版本回報 947 段紅色交線，紅線沿整個上緣、左右接合縫與正常插入位置跑；即使不補回固定截角，整片 production EndCap 仍可產生數百段假交線。
- **根本原因**：surface/triangle crossing 只能回答兩個 mesh 表面是否相交，無法自行理解「這條是設計上允許的 mating seam」。把整片 EndCap 當 target，就會把正常貼合／插入接觸也一起掃進來。這不是視覺顏色問題，而是 probe ownership 錯。
- **正確做法**：固定截角診斷 target 必須先做 `restored - production`，只折起並加厚這個 **relief delta**；再拿它與 BoxBody physical solid 求穿越。標準金庫型本測試環境因此由 947 段整圈假紅縮成 454 段局部交線（Head 227 + Tail 227），只集中在固定截角角落。
- **視覺規則**：因 target 已限制成 relief delta，可把真正命中的 delta triangles 畫成半透明紅面，再疊紅色實線 intersection segments；禁止把整片 EndCap 的 hit triangle 染紅。
- **關閉診斷**：未勾 `診斷時忽略固定截角` 時，不得退回整片 EndCap 求碰撞；停止固定截角 probe 並提示使用者先啟用該診斷。
- **ownership 防線**：renderer 不得直接 import `assembly_collision`；純幾何／delta helper 放既有 `assembly_geometry`，production relief solver 仍留在 `assembly_collision`。
- **交付防線**：AI 在交付碰撞視覺前必須自己至少檢查 Head、Tail 兩個視角；若紅區沿正常長接縫擴散，視為不合格，不得叫使用者代驗收。
- **防錯測試**：assert `restored_endcap_relief_delta` 只含補回材料；renderer collision target area 必須小於整片 EndCap；ignore=false 時 detector 不得被呼叫；delta hit triangles + solid intersection lines 可局部顯示。


### 60. 3D 干涉能畫紅區，不代表已得到可生產截角尺寸

- **淨空防線**：A 在收斂後做正交軸向精確擴張，不使用 polygon buffer 斜接；標準測件 A=5 應由 `39×38 + 14×4` 精確變成 `44×43 + 19×4`。
- **數值防線**：對稱件若左右 canonical shape 只差 <0.01~0.02 mm 級 tessellation noise，可在嚴格 Hausdorff 容差內取 union；不得把真正非對稱差異抹掉。
- **BEND 防線**：dynamic cut 比 legacy fixed cut 少切時，BEND 也必須依新 material 重 clip；本標準測件左 X BEND span_start 由 legacy `42` 恢復為 `38`，FW 水平 BEND 左端由 `16` 恢復為 `14`。CUTTING 對但 BEND 還舊，仍視為未完成。

### 80. 長任務只在聊天或臨時工作樹記進度，下一回合就失去真正續跑點
- **錯誤現象**：已跑到 440/1291、940/1291 等進度，但容器/工作樹重置後只剩對話文字，無法證明 completed nodeids、collection SHA 或已套 patch，只能重跑或猜。
- **根本原因**：把聊天回報當 durable Source of Truth，沒有獨立 **durable checkpoint**。
- **正確做法**：長 profiling/stress/release 任務固定落 `/mnt/data` 或其他跨回合持久位置；保存來源包、patch/hash、collection SHA/count、journal/state、completed/pending/failed、效能計數與下一步命令。每個時間片結束更新同一 checkpoint。
- **禁止**：下一回合不得從聊天文字猜「大概跑到哪」；先讀 durable state。

### 81. 用跑過 pytest 的目錄做 FULL vs UPDATE overlay 比對，會被 __pycache__/.pytest_cache 製造假 mismatch
- **錯誤現象**：UPDATE 覆蓋後共同檔案 SHA 全相同，但樹檔案數仍不一致，看起來像 UPDATE 漏檔。
- **根本原因**：FULL 驗證目錄先跑過 Python/pytest，新增 `__pycache__/.pytest_cache/.pyc` 等測試產物；overlay 目錄是 pristine，兩邊不是同一比較條件。
- **正確做法**：FULL/UPDATE overlay 最終逐檔比較必須使用兩個**pristine、從未執行 Python/pytest 的 fresh extraction**。測試目錄與封包完整性比較目錄分離。
- **防錯**：先驗 archive entry/CRC，再在 pristine extraction 做 missing/extra/hash mismatch；測試產物一律排除。

### 82. 1291 顆 regression 全過，不等於 GUI 真實連續操作一定順
- **錯誤現象**：單元/整合測試全綠，但使用者快速改尺寸、切板件、切 Family/Assembly Intent、連續操作 3D 時仍可能卡頓或事件暴增。
- **根本原因**：一般 regression 驗功能 oracle，未必覆蓋「短時間多事件」與 wall-time/call-count 行為。
- **正確做法**：GUI 效能修改另設**真 GUI 壓力** gate：連續 W/H/D/T burst、箱身/封頭/封尾快速切換、Family/Assembly Intent 切換、3D 開關/互動；逐步記 wall time、recalculation、DXF disk read、manufacturing resolve、render，並驗最終 state/scene 不 stale。
- **禁止**：只用 headless 或「1291 PASS」宣稱 GUI 不會卡。

### 83. release runner 只看到父程序先退出就 return，process group 子程序可能仍存活
- **錯誤現象**：timeout cleanup 後 pytest/Python parent 已退出，但 child process 偶發仍是 running；下一批被孤兒程序拖慢，測試又出現不穩定 timeout。
- **根本原因**：`_kill_process_group()` 在送 SIGTERM 後只等待 parent exit；父程序先退出就提前 return，沒有確認同一 process group 的 descendants 已全部消失。
- **正確做法**：process group cleanup 的完成條件是整個 group 消失，不是 parent `poll()!=None`。TERM 後仍需檢查 group，必要時 KILL；測試應驗 child tree 真正消失。
- **測試防線**：不要把「child PID 必須在 1 秒內建立」混成 kill-tree oracle；先確保 child 已啟動，再驗 timeout cleanup。flaky startup timing 與 process-group cleanup correctness 必須分開。

### 84. release runner `--reset` 先刪 journal 再搶 lock，會在「鎖拒絕」時仍破壞 durable evidence
- **錯誤現象**：舊 runner 正持有 journal lock 並正常續跑；第二個 runner 對同一 journal 執行 `--reset`，最後雖回報「journal already in use」，原 journal 的 collection header 卻已被刪掉。舊 runner 接著只會追加 batch 記錄，形成「有 completed nodeids、沒有 collection SHA/count」的無效 release evidence。
- **根本原因**：CLI reset 順序是 `unlink journal/state → acquire run lock`。run lock 只能阻止第二個 runner進入執行區，無法復原它在搶鎖之前已完成的破壞性檔案操作。
- **正確做法**：所有 reset/unlink 必須搬進 `journal_run_lock(...)` 之內：`acquire lock → 若 reset 則 unlink journal/state → 建立/驗證 collection header → 執行 suite`。持鎖失敗必須 fail closed，不能觸碰既有 journal/state bytes。
- **防錯測試**：真啟動一個持鎖 runner，再對同一 journal 執行第二個 `--reset`；第二個必須被拒絕，且前後 journal bytes/header 完全相同。只 mock lock helper 不算，因為這個坑就是 CLI ordering。

### 85. Scheduler 已成唯一 executor 後，legacy partial GUI fixture 缺 seam 不能靠 production fallback 救
- **錯誤現象**：完整 suite 只有舊 `SimpleNamespace` / `__new__` fixture 直接呼叫 GUI handler 時出現 `AttributeError: ... _request_phase6_update`；真 `BoxCalculatorGUI` 與正式 GUI 流程正常。若為了讓這顆舊測試過，在 handler 寫 `hasattr(...)` 後直接 `update_calculations()`，表面綠燈卻把 Scheduler 唯一執行權重新打破。
- **根本原因**：架構 seam 已升級，但 partial test double 還停在舊 handler interface；把 fixture 缺介面誤判成 production 相容性需求。
- **正確做法**：先確認真 production instance 一定擁有 Scheduler seam、且測試 oracle 並非在驗「沒有 Scheduler 時仍可運作」。若成立，更新 test fixture 使其提供 `_request_phase6_update(...)` 等正式 seam；禁止在 production 增加 direct calculation/do_update fallback。
- **防錯測試**：Scheduler ownership regression 必須繼續鎖住 direct executor bypass；legacy handler fixture 只 stub 正式 request seam。等價 part switch/display-only 操作應驗 `render=1、full calculation=0`，不要保留舊的 `update=1` oracle。

### 86. FULL / UPDATE 把 `.git/**`、`.scratch/**` 當正常差異檔收進正式包
- **錯誤現象**：`PHASE6_BOXBODY_ENDCAP_DOOR_RECEIVING_*_20260904_092052.zip` 重驗時，FULL 與 UPDATE 都出現 270 個 `.git/**` entry，另有 69 個 `.scratch/**`；UPDATE 甚至包含 `.git/config`、`.git/index`、refs、objects、logs。功能 regression 可以全綠，但直接覆蓋 UPDATE 仍可能污染使用者本機 Git repository，`.scratch` 也把 journal/checkpoint/debug 中繼資料帶進正式交付。
- **根本原因**：`tools/phase6_release.py` 的共用 `_is_packaged_file()` 只排除 cache/`.pyc`，而 `excluded_update_roots` 只處理 `BACKUP`。collector 因此把 `.git/.scratch` 視為一般 source files；pristine FULL vs baseline+UPDATE parity 若兩邊都使用同一套錯誤 collector，仍可能得到假綠燈。
- **正確做法**：在 `release_required_artifacts.json` 建立 FULL/UPDATE 共用的 `excluded_package_roots` Source of Truth，至少包含 `.git`、`.scratch`；FULL collector、UPDATE diff collector、mandatory tree collector 與 final entry-policy gate 全部共用同一規則。
- **防錯驗證**：release regression 必須建立含 `.git/config`、`.git/index`、`.scratch/*.jsonl` 的 synthetic source tree，先證明舊 collector 會收檔，再驗修正後 FULL/UPDATE 都為 0 entry。正式 ZIP 另直接列 entry 斷言 `.git/** == 0`、`.scratch/** == 0`；不能只看 CRC、SHA、功能測試或 pristine parity。
- **禁止**：不得用「FULL 是完整專案」合理化把 repository internals 打進 FULL；不得只排 UPDATE 而讓 FULL 繼續帶 `.git`；不得只在壓縮後手工刪 entry，collector/policy/test 必須同時修正。


### 87. Tk/Xvfb targeted gate 只印出點號就卡住，不能把「測試 body 看似跑完」當 PASS
- **錯誤現象**：兩顆 Assembly/GUI probe 各自單跑可 PASS，但串在同一 pytest/Tk/Xvfb process 時只看到點號或局部進度後程序不退出。若只憑「斷言應該已跑完」或 wrapper timeout 前的點號就記成完成，會把 order-dependent Tk grab、interpreter teardown 或 child process 殘留掩成假綠燈。
- **根本原因**：把 test body completion、pytest final summary、interpreter teardown、Xvfb/wrapper lifecycle 四層證據混成同一個完成訊號。點號只表示某 nodeid 已走到 pytest progress reporter，不保證整批有完整終態。
- **正確做法**：`complete_teardown_timeout` 只接受 pytest 已輸出**完整 PASS summary**（`N passed` / `N skipped` 且無 failed/error）。只有點號、百分比或局部 nodeid 輸出時一律先記 `incomplete_timeout`；kill 整個 process group，再以單 nodeid、prefix/binary isolation 判斷是否為 order-dependent teardown。單跑 PASS 只能證明該 nodeid 本身，不可替代原串批次的終態。
- **防錯測試**：派工 Skill 契約必須明文包含「完整 PASS summary」與「只看到點號不得標記 complete_teardown_timeout」；runner 測試需分別覆蓋完整 summary 後 hang 與只有 progress dots 後 hang。

### 88. fresh extract / checkpoint restore 覆蓋部分工作樹，形成新舊檔混合的 execution tree
- **錯誤現象**：T03 已驗收後繼續 T04/T05，執行目錄中部分檔案被 fresh extract 回舊版，另一些仍保留新修改；若只看目前檔案存在、mtime 或聊天紀錄，會在**混合狀態**上繼續開發，後續 targeted gate 的結果失去可追溯性。
- **根本原因**：checkpoint 只被當「有 ZIP 可下載」，沒有把來源包與已驗收檔案 SHA 建成 **checkpoint provenance**；journal 又只綁 pytest collection identity，無法偵測 source tree 已被部分覆蓋。
- **正確做法**：每個已驗收 checkpoint 保存來源 FULL/上一 checkpoint SHA256 + 本工單修改檔 SHA256 manifest，產生可重算的 **execution tree fingerprint**。任何 fresh extraction、restore、runtime 重建後，resume 前都要與**最近已驗收 checkpoint**比對。fingerprint 不符即 fail closed，標成混合狀態，隔離該目錄並從最近 checkpoint 在乾淨目錄完整恢復；不得靠 mtime 或挑檔補拷貝拼回去。
- **防錯規則**：`collection SHA ==` 只代表測試集合相同，不代表 production/source tree 相同；長回歸 resume 必須同時通過 collection identity 與 checkpoint provenance。

### 89. 把 UPDATE baseline 的具體 FULL 檔名寫死在 release manifest / Skill，下一輪一定引用歷史包
- **錯誤現象**：`release_required_artifacts.json` 或 release Skill 保存某一輪 `PHASE6_*_FULL_YYYYMMDD_HHMMSS.zip`；下一輪出包時工具仍強制比對該歷史檔名，導致正確的新 baseline 被拒絕，或更糟地自動拿歷史資料算 UPDATE。
- **根本原因**：把「每輪 release 的執行輸入」誤建模成「永久 policy 設定」。baseline 身分會隨每輪來源 FULL 改變，不具有可永久硬編碼的值。
- **正確做法**：`release_required_artifacts.json` 只宣告 `update_baseline_mode: explicit_runtime_archive`，**不得保存任何具體 FULL 檔名、日期或時間戳**。本輪 baseline 必須由 release controller / durable release state 以 runtime `baseline_archive` 明確傳入；tool 只驗存在性、ZIP 格式/CRC 與本輪 provenance，不得自行搜尋「最新」或回退歷史包。
- **防錯測試**：policy regression 必須斷言 manifest 不存在 `canonical_update_baseline_archive`，且兩個不同名稱/時間戳的合法 FULL ZIP 都能通過 runtime baseline validator；release Skill 另掃描禁止出現具體時間戳 FULL baseline。
- **禁止**：不得用「改成這一輪檔名」修這個問題；那只是把錯誤延後到下一輪。也不得用聊天記憶、Library 排序、mtime 或檔名最大值自動猜 baseline。

### 90. 容器 DNS 壞掉後把 GitHub Connector 內容同步誤稱成 `git push`
- **錯誤現象**：容器因 `Could not resolve host` 無法直接 `git push`，改用已授權 GitHub Connector 寫入遠端；若之後直接宣稱「已 push 整個 branch」，會混淆 Git transport 與 Contents/Commit API 同步，且大型 JSONL、ZIP 或本機 commit identity 可能根本沒有被同步。
- **根本原因**：沒有區分「本機 commit graph 的 Git push」與「透過 Connector 建立新的遠端 commit/更新檔案內容」；工具中途報錯時又假設全成或全敗，可能重送已成功操作。
- **正確做法**：先以 `git ls-remote`/DNS probe 確認 transport blocker；Connector fallback 前記錄遠端 HEAD，所有 ref update 使用 `force=false`。批次錯誤一律視為可能部分成功，先重新讀取 remote HEAD/檔案/compare，只補缺項。完成後從 GitHub 遠端重新讀回關鍵 evidence/state，並逐項確認 binary/ZIP/raw journal 是否存在。
- **防錯規則**：Connector fallback 只能回報「已透過 GitHub Connector 同步遠端內容」；除非真正 Git transport 成功，不得說 `git push` 成功。若任務要求保留本機 commit SHA/history，而 Connector 無法精確保留，必須 fail closed 並回報 Git transport 仍受阻。

### 90. 把已知 Cabinet Family 的「上次 runtime 編輯」當成下次 preset，會讓切盤型語意反轉
- **錯誤現象**：受電箱預設是 800/1600/350，但使用者改成 820/1700/360、切去金庫型再切回受電箱後，程式又恢復 820/1700/360；更嚴重時 Receiving → 自訂會因 family fallback 把舊 Vault 400/600/250 叫回來，完全違反操作預期。
- **根本原因**：用 `_cabinet_family_runtime` 這類 per-family session cache 同時扮演「preset」與「目前 runtime」；又把自訂 fallback 成某個 known family，導致 carry-forward 與 preset reset 兩種語意混在一起。
- **使用者確認的正確規則**：**已知盤型切到哪一型，就套該型自己的 canonical preset；只有切入「自訂」才沿用切換當下目前值。** 自訂切回已知盤型時重新套 target preset。
- **2D/3D 一致性**：Main GUI 與 3D Designer 必須讀同一 known-family preset source；從 Receiving 直接在 3D 切 Vault 時，除了 W/H/D/T/FW，也要恢復 Vault structure / topology，不能留下 Receiving 三件式結構。
- **Persistence 邊界**：family preset 只在使用者明確切換 known model 時套用；Project Save/Reload、live snapshot apply、redraw/refresh 不得觸發 fresh preset。供 3D 使用的 `_runtime_family_presets` 只能是執行期 metadata，不得進 `.p6fold`。
- **防錯測試**：固定覆蓋 Known→Known、Known→Custom、Custom→Known，以及「Main 已在 Receiving 才開 3D → 3D 切 Vault」；另 assert project snapshot 不含 runtime preset metadata。

### 91. 把 Receiving 底板 55 mm family shrink 當成 seam relief 而清成 0，會讓 2D/3D/DXF 全鏈尺寸錯一層
- **錯誤現象**：受電箱 family 明明應有 Top/Bottom/Left/Right 各 55 mm 的底板縮量，舊程式卻在 `manufacturing_api` 看到 Receiving 就把 `st/sb/sl/sr` 強制設為 0；Main 2D 與 3D 又各自用 `base_w=W/base_h=H` 特例補錯。結果 W=800/H=1600 時展開外框變 830×1630，而不是正式 720×1520。

### 92. Receiving 只藏 symmetry checkbox、卻保留 `state.symmetric=True`，會讓非對稱 family 暗中繼續鏡像
- **錯誤現象**：受電箱畫面看似沒有對稱設定，但原始 Fold Designer 的 `AppState` 每次初始化都預設 `symmetric=True`；重新開 3D／Save-Reload 後又恢復有效對稱，甚至刪折與改折仍會鏡像另一側。

### 93. Receiving placement 由 consumer 自算 front/origin，會讓 Door／Frame／Divider 各活在不同世界座標
- **錯誤現象**：Door 在 Bridge 自算 X/Y 後再交給 `front -> depth/2`，top/left/right inner frame 因沒有正式 resolver 而退回 `(0,0,0)`，2D overview 又用 `50*scale` 自畫；結果 2D、3D、collision 即使看的是同一盤，實際 transform 並不相同，重建後還可能跳位。

### 94. Inner Door 的 80 mm 若做成全域 Z magic constant，會破壞每門獨立 datum 與 family coordinate
- **錯誤現象**：多門 Receiving 中，所有內門／框都直接做 `Z-80`；只要外門 datum、family 朝向或某一片門的設定不同，就會互相污染或放到錯誤深度。
- **根本原因**：把「相對自己的外門面往箱內退 80」誤建模成世界座標常數，而不是每片 Door 的相對 assembly state。

- **Persistence**：這個值是 authoritative project state，必須 Save/Reload；舊 project 缺欄位時依 family default=80 遷移，不得寫第二套 runtime cache。
- **UI**：每片外門的「內退 mm」輸入直接寫同一 item；勾掉內門時輸入停用，重新啟用取得該 family default 或既有值。
- **防錯測試**：固定覆蓋 fresh 80、兩扇門不同 offset、Entry commit、Save/Reload、placement source 不含 hard-coded `-80`。


### 95. Remote QA 只觸發 workflow 就停止，會把「尚未驗證」誤當成「已開始所以可收尾」
- **錯誤現象**：同步遠端後建立 GitHub Actions QA，回報「已啟動／正在跑」就結束回合；run 可能稍後才失敗，ticket 卻沒有 log 判讀、修復、cleanup 或 durable terminal evidence。
- **根本原因**：把 remote QA trigger 當成動作完成，而不是需要持續觀測到終態的條件迴圈。
- **正確規則**：remote QA 一建立 run 就啟動 `monitoring-remote-qa`。持續追 run → jobs → steps；failure 立即讀 failed-job log、分類 production vs harness、修正／重跑受影響範圍並繼續監控。
- **成功也不是立即完成**：必須抓 exact PASS/FAIL/invariant evidence、清 one-shot workflow/trigger、遠端反讀確認清理、寫 checkpoint/journal/state，才可 ACCEPT / close。
- **禁止**：queued / in_progress / 「已 retrigger」都不得作為停止理由；進度回報只是觀測點，不是任務終點。

### 96. 把「逐片資料列」當成「逐片輸入區」，會讓 physical piece 已存在但操作仍像單一箱身
- **錯誤現象**：二件式／三件式的 3D 與資料區已經有 2/3 個真 physical pieces，但箱身設定區仍只有一個共同參數框，下面僅以文字列出各片尺寸；使用者無法辨識每個輸入屬於哪一片。

- **正確規則**：child input section 必須直接由已解析的 physical `render_data.pieces` 建立；section 的 stable id 就是 `box_body:<role>`。輸入仍寫既有 `box_body_structure_state`，不得新增 fake child model。
- **切換／Persistence**：二件式 ↔ 三件式時整頁依 current pieces 重建並 destroy stale sections；Save/Reload 也從 persisted structure state → resolved pieces → UI projection 重建。
- **共享參數**：中央接合折邊、共用 relief 等仍是 structure-level state，不得為了「每片一區」而複製到某一片造成多份 authority。
- **防錯測試**：同時 assert section count、section stable id == physical piece stable id、切換後舊 widget 已 destroy、Save/Reload parity，以及 R10 真 physical-piece guard。
