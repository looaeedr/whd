# Door Layout and Export Mirror Design

## Goal

Improve Door input and rendering so multi-door layouts are visually intuitive, dimensions auto-complete from cabinet W/H, and every Door DXF is permanently exported as a left-right mirror while internal geometry and GUI remain in the normal editing orientation.

## Scope

This change affects Door configuration, Door GUI layout visualization, Door size derivation, and Door DXF export orientation.

It does not change global W/H/D semantics, Door FourSideFlange topology, structural geometry generation, hole-editing coordinates, or non-Door part export orientation.

## 1. Source Dimensions

Global inputs keep their current meaning:

- `W`: whole cabinet width.
- `H`: whole cabinet height.
- `D`: whole cabinet depth.

Multi-door subdivision is configured only in the Door area. W/H/D are not replaced by per-door inputs.

A Door layout consists of ordered columns. Each column has a width and ordered vertical segment heights.

Example:

```text
W = 1100
H = 1800

Column 1 width = 600
  heights = 600, 500, 700

Column 2 width = 500
  heights = 800, 1000
```

## 2. Visual Door Layout Editor

Do not use a per-door Preview radio/button workflow.

The Door page displays the whole subdivision at once in cabinet orientation:

- widths run horizontally from left to right;
- heights run vertically from top to bottom;
- every cell is visible simultaneously;
- cells contain no metadata text; the program keeps cell identity/edge state internally;
- edited hole/blind-hole/indicator geometry is rendered inside the owning cell;
- column width Entry widgets are positioned horizontally above their columns;
- height Entry widgets are positioned vertically with their segments;
- the old stacked column/layer configuration panel is not shown;
- changing a value redraws the complete layout immediately.

The drawing represents the cabinet subdivision relationship, not multiple unfolded Door sheets overlaid in one canvas.

## 3. Automatic Remainder Completion

Widths and heights use the same remainder rule.

### Widths

Given total cabinet width `W`, the last column is automatically filled with the remaining width.

Example for `W = 1200`:

```text
User enters 700
=> 700, 500(auto)

User edits 500(auto) to 300
=> 700, 300, 200(auto)
```

### Heights

For each column independently, given total cabinet height `H`, the last segment is automatically filled with the remaining height.

Example for `H = 1000`:

```text
User enters 400
=> 400, 600(auto)

User edits 600(auto) to 400
=> 400, 400, 200(auto)
```

### State rule

The current last remainder cell is generated by the program. If the user edits that generated value, it becomes a fixed user value and a new remainder cell is appended when the remainder is positive.

Deleting or changing any fixed value recomputes the current remainder.

The UI must not create zero or negative remainder cells. If fixed values exceed W or H, the layout is invalid and must visibly report the excess rather than generating a negative cell.

## 4. Door Starting-Size Rule

Each subdivision cell provides the starting width and height for one Door calculation.

The existing single-door algorithm remains the reference for a cell that has the full surrounding cabinet edges.

The subdivision only changes how much cabinet-frame allowance is deducted from the starting size:

- if a cell has another column to its right, its right cabinet edge is absent, so width deducts one fewer `FW + 2T` allowance;
- if a cell has another segment below it in the same column, its bottom cabinet edge is absent, so height deducts one fewer `FW + 2T` allowance;
- the rightmost cell retains the right-edge deduction;
- the bottommost cell retains the bottom-edge deduction.

This does **not** remove Door sheet-metal flanges. Every resulting Door remains the existing FourSideFlange topology.

The existing gap behavior remains unchanged unless a separate manufacturing rule is later specified.

## 5. Door Selection / Editing

All cells remain visible. Single-click selects a Door cell. Double-click opens that exact cell in the unified hole editor; selection never hides the other cells or changes the layout into a one-door preview mode.

Each multi-door cell owns an independent feature list and independent direct-door-indicator settings. Editing one cell must not add holes to another cell. After the editor closes, the whole-layout Canvas redraws the edited features inside their owning cell.

The Door page itself visibly keeps only the `啟用多門配置` control. Direct Door indicator controls are located inside the unified Door hole editor. The independent indicator-box settings-page entry is located outside the Door page.

The layout is the source of truth for which Door instance is being edited/exported.

## 6. Door DXF Left-Right Mirror

Door geometry is kept in the current normal orientation during all internal work:

```text
input
-> Door size derivation
-> structural geometry
-> holes/features
-> DrawingScene
-> GUI/editing
```

Only Door DXF output applies the permanent left-right mirror:

```text
Door DrawingScene
-> export-only horizontal mirror
-> DXF serialization
```

The mirror axis is the exported Door scene's horizontal center:

```text
x_out = min_x + max_x - x
```

All Door manufacturing geometry and annotations that carry position must transform consistently, including CUTTING, BEND, holes, blind holes, MARKING, DATUM, CHECK, and other Door scene primitives.

The mirror is not exposed as a user option. It is the fixed Door export convention.

The following must remain unmirrored:

- GUI Door editing view;
- internal canonical Door geometry;
- Door input coordinates;
- non-Door parts.

This prevents double-mirroring in multi-door mode and keeps editing coordinates intuitive.

## 7. Output Naming

Multi-door DXF files continue to be one file per subdivision cell, for example:

```text
door_c1_r1.dxf
door_c1_r2.dxf
door_c2_r1.dxf
```

Each of these files receives the same export-only left-right mirror.

Single-door output also receives the same export-only mirror so single-door and multi-door conventions never diverge.

## 8. Validation and Regression Tests

Formal tests stay under `tests/`. One-off generated files and manual inspection artifacts stay under `tmp/`.

Required regression coverage:

1. Single Door sizing remains identical to the previous single-door calculation before export transform.
2. Multi-column/multi-row edge allowance derivation is correct.
3. Width remainder auto-completion works and promotes an edited auto remainder to a fixed value.
4. Height remainder auto-completion works independently per column.
5. Deleting/editing fixed values recomputes the remainder.
6. Oversubscribed width/height reports invalid state and creates no negative remainder.
7. Whole-layout GUI displays all cells with horizontal width Entries and vertical height Entries, with no cell metadata text.
8. Selecting a cell does not hide the whole-layout visualization; double-click opens the owning cell editor.
9. Door GUI/canonical geometry remains unmirrored.
10. Single-door DXF is left-right mirrored at export.
11. Every multi-door DXF is left-right mirrored exactly once.
12. Door holes/features and manufacturing layers mirror together with CUTTING/BEND geometry.
13. Multi-door user holes and direct indicator settings export only to their owning cell DXF.
14. Door indicator controls live in the unified Door hole editor, not on the Door page.
15. Existing end-cap/head mirror regression remains passing.

## Architecture Boundary

- `gui.py`: Door layout input, Canvas-embedded dimension Entries, all-cells hole visualization, cell-specific editor routing, indicator-editor UI, selection interaction, remainder-input UX. No manufacturing geometry formulas.
- `sheetmetal_part_adapters.py` / Door sizing policy: turn layout cell + edge-presence state into the existing Door builder inputs.
- `sheetmetal_geometry.py`: unchanged Door structural topology.
- `sheetmetal_features.py`: unchanged canonical feature coordinates.
- `sheetmetal_drawing.py`: canonical scene/primitives remain normal orientation.
- `ae.py` / Door DXF export boundary: apply the Door-only horizontal transform immediately before serialization, without creating a second geometry implementation or serializer.

## Non-Goals

- No automatic DXF drawing recognition.
- No changes to cabinet W/H/D entry semantics.
- No new named layout modes such as `left1_right2`.
- No per-door mirror checkbox.
- No topology variants for top/middle/bottom doors.
- No changes to bottom plate or middle plate derivation in this implementation unless separately specified.
